# GraphQL API Design

Principles for schemas that stay evolvable, servers that stay fast, and clients that stay
consistent. Grounded in the Relay Connections spec, the Shopify graphql-design-tutorial,
GitHub's public API, Marc-André Giroux's *Production Ready GraphQL*, and Apollo/DataLoader
documentation. Each reference file cites its sources.

Read the reference that matches the work:

- Designing or changing types, fields, mutations, pagination, or enums → [references/schema-design.md](references/schema-design.md)
- Writing or reviewing resolvers, loaders, authorization, subscriptions → [references/server.md](references/server.md)
- Consuming the API: queries, fragments, cache updates, error handling → [references/client.md](references/client.md)
- Querying from a React app: hooks, loading/error states, Provider setup, where to query vs. pass fragment refs, Apollo vs urql → [references/react.md](references/react.md)

## Core principles

**Design around the business domain, not the database.** The schema is an API for behavior,
not a mirror of tables. Expose use-case fields (`isEligibleForRefund`) alongside raw data,
name mutations after business actions, and never leak implementation details (join tables,
internal state machines) into types or their descriptions: descriptions are written for the
consumer and never reveal or rely on the code under the hood. If a schema could be
autogenerated from the database, it isn't designed yet.

**Start minimal.** Adding a field is always safe; removing one is a breaking change. Every
field needs a concrete use case today, not a hunch about tomorrow.

**Mutations are behaviors with contracts.** One mutation per logical business action
(`approveReview`, not a generic `updateReview` with optional everything), taking a single
required input object and returning a dedicated payload that carries the changed entity plus
`userErrors`. Expected failures are data the client renders; top-level GraphQL errors are
reserved for bugs, auth failures, and infrastructure. Never return a bare `Boolean`.

**Nullability is a semantic and failure-isolation claim, decided per field.** Non-null for
arguments, input fields the operation genuinely requires, identity fields, and values you can
always produce. Nullable for anything backed by an association, network call, or fallible
work: under partial failure, a non-null field nulls out its parent, and `[T!]!` nulls the
whole list on one bad element. Going non-null → nullable is a breaking change; the reverse is
safe, so when unsure, start nullable.

**Paginate anything that grows, with spec Relay connections.** `XConnection` / edges /
nested `PageInfo`, `first`/`after` args. Standard tooling (Apollo `relayStylePagination`,
codegen) works unmodified against the spec shape and fights anything else. Unpaginated lists
that grow are a breaking change waiting to happen.

**Any field resolver that fetches goes through a per-request DataLoader.** A per-parent
service call in a field resolver is the N+1 anti-pattern: a list of 50 parents means 50
queries. Loaders also deduplicate repeated lookups within a request.

**Evolve additively; never surprise a client.** New fields and types anytime. Retire fields
with `@deprecated(reason:)` naming the replacement; removal only through a deliberate,
usage-tracked process. Treat enum-value additions as dangerous: clients must tolerate
unknown values.

**The client's normalized cache is the source of truth for server data.** Fragments colocate
with the components that render them; mutations update the cache from the returned payload
entity (plus `optimisticResponse`), not by refetching the world. This holds for Apollo's
`InMemoryCache` by default; urql needs Graphcache, since its default document cache is not
normalized (see [references/react.md](references/react.md)).

**In a React app, query at route boundaries and pass fragment references down.** A component
below the boundary declares a fragment and receives a fragment ref, not the parent query's
scalar fields: a query in every leaf causes waterfalls, and a top query enumerating every
descendant's fields couples the query to all of them. See [references/react.md](references/react.md).

## Working in an existing schema

Real schemas accumulate conventions that diverge from the ideal. Two different shapes for the
same concern cost more than one nonstandard shape, so:

- **Mild divergences: match local convention.** Nonstandard connection naming, an existing
  enum's casing, an established input-object style: extend the pattern that's there. Adding a
  second page of a paginated list in a new shape breaks every consumer of the first.
- **Real defects: apply the ideal even next to old code.** A *new* mutation gets a payload
  with `userErrors` even if its neighbors return `Boolean`; a *new* field resolver gets a
  DataLoader even if the rest of the file does per-parent fetches; client error handling
  covers both channels even where the surrounding code swallows. These are contracts, and new
  surface area is the only cheap place to get them right.
- **Never mix both shapes in one type.** A type with half its lists offset-paginated and half
  connection-paginated is worse than either convention alone.

When a divergence is load-bearing enough to matter (an error contract, a pagination shape),
name it to the user and propose the migration as separate work: don't silently entrench it,
and don't silently rewrite it either.
